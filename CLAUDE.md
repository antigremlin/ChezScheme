# CLAUDE.md — Chez Scheme

This file provides guidance for working on the Chez Scheme codebase with Claude Code.

For a full architectural overview see [`architecture.md`](architecture.md).

## Quick Reference

| What | Where |
|------|-------|
| Scheme compiler + libraries | `s/` (94 `.ss` files) |
| C runtime kernel | `c/` (~49 C/H files) |
| Test suites | `mats/` (94 `.ms` files) |
| Build orchestration | `build.zuo`, `Makefile` |
| Configuration | `configure` shell script |
| Bootstrap boot files | `boot/pb/` |
| Documentation source | `csug/`, `stex/` |

## Build

```bash
# Configure (auto-detects machine type; run once)
./configure

# Full build (bootstrap + native compile)
make

# Build just the C kernel (faster iteration on c/ changes)
make kernel

# Run without installing
make run

# Run the test suite
make test

# Parallel tests
make test JOBS=8

# Cross-compile boot files for another machine type
make boot XM=<machine-type>   # e.g., XM=tarm64le
```

The build workarea is a directory named after the machine type (e.g., `ta6le/`). Intermediate `.so` files and the final `bin/` live there.

Machine type naming: `[t]<arch><os>` — the `t` prefix means threaded.
Common types: `ta6le` (x86-64 Linux), `ta6osx` (x86-64 macOS), `tarm64le` (AArch64 Linux), `ta6nt` (x86-64 Windows).

## Editing the Compiler (`s/`)

Scheme source files in `s/` are compiled during the build into the boot files. After editing a file you must rebuild to see the effect:

```bash
make           # rebuilds everything that changed
```

Key files to know:

| File | Role |
|------|------|
| `s/cmacros.ss` | Object layouts and type tags — the shared vocabulary between compiler and C runtime |
| `s/syntax.ss` | Hygienic macro expander |
| `s/cpnanopass.ss` | Main compiler (nanopass IR passes, instruction selection) |
| `s/cpprim.ss` | Primitive inlining |
| `s/cp0.ss` | Source-level optimizations (constant folding, dead code, inlining) |
| `s/cptypes.ss` | Type inference |
| `s/compile.ss` | Public compilation API (`compile-file`, `compile-program`) |
| `s/x86_64.ss`, `s/arm64.ss`, … | Architecture backends |

The compiler uses the **Nanopass framework** (`nanopass/` submodule). Each pass operates on a typed intermediate language. When adding a new pass, define the input/output languages and the pass transformation.

Platform-specific constants live in `.def` files (e.g., `s/ta6le.def`), generated from `s/unix.def` / `s/tunix.def` templates.

## Editing the Runtime (`c/`)

C changes require recompiling the kernel:

```bash
make kernel
```

Key files:

| File | Role |
|------|------|
| `c/gc.c` + `c/gc-*.inc` | Garbage collector — `gc-ocd.inc`, `gc-oce.inc`, `gc-par.inc` are generated by `s/mkgc.ss` |
| `c/alloc.c` | Object allocation |
| `c/fasl.c` | Fasl loader / linker |
| `c/foreign.c` + `c/ffi.c` | Foreign function interface |
| `c/thread.c` | Threading |
| `c/scheme.c` | Thread context (TC) and heap init |
| `c/system.h` | Master runtime header |

**Do not edit `gc-ocd.inc`, `gc-oce.inc`, or `gc-par.inc` directly** — they are generated from `s/mkgc.ss`.

## Running Tests

```bash
make test              # all tests, default configuration
make test TESTS=foo    # run only mats/foo.ms
```

Test files are in `mats/*.ms`. Each file exercises a subsystem (e.g., `cp0.ms`, `foreign.ms`, `bytevector.ms`). Tests run under multiple optimization/configuration combinations; expected-error output lives in `mats/root-experr*` files.

To add a test: add a `(mat <name> ...)` form to the relevant `.ms` file.

## Adding a New Primitive

1. Declare the primitive in `s/primdata.ss` (name, arity, flags).
2. Add inlining logic in `s/cpprim.ss` (optional but important for performance).
3. Implement the generic (non-inlined) version in the appropriate library file under `s/` (e.g., `s/5_1.ss` for basic primitives).
4. Add tests in `mats/`.
5. Rebuild.

## Adding a New Platform

1. Create a `.def` file for the new machine type (copy the closest existing one).
2. Add the machine type to `configure` and the `Makefile` templates in `makefiles/`.
3. If the architecture is new, add or extend a backend file in `s/` (e.g., `s/newarch.ss`).
4. Cross-compile boot files from an existing host: `make boot XM=<new-machine-type>`.
5. See `IMPLEMENTATION.md` for detailed guidance.

## Bootstrapping

Chez Scheme is a **bootstrapped compiler**. The pre-built portable bytecode boot files in `boot/pb/` bootstrap the build on any platform. After the first build the native boot files in the workarea take over.

If you break the compiler badly enough that the build fails to bootstrap, restore from `boot/pb/` or a known-good native boot snapshot.

## Code Style

- Scheme files use 2-space indentation following standard Scheme conventions.
- Macros defined in `s/cmacros.ss` are used pervasively — read that file when you encounter unfamiliar names.
- The nanopass IR types and pass contracts are the source of truth for the compiler's internal structure; when in doubt read the nanopass language definitions at the top of `s/cpnanopass.ss`.
- C code follows the style of the existing `c/` files (K&R braces, 2-space indent).
